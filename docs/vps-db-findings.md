# VPS既存DBの調査とランキング設計

調査日：2026-10-12（JST）。SSHで読み取りのみを実施。既存サービス、DB、認証ファイルへの書き込みや停止は行っていない。

## 決定済み

- 日本語向けワールドを掲載する。
- 掲載判定は名前・説明・タグにある日本語または日本向けの明示を中心にする。作者名だけを根拠に掲載しない。手動で追加・除外できるようにする。
- 1時間刻みでランキングを更新する。
- 総同接とパブリック人数を同じ一覧で比較する。
- 表示はTOP100。毎時、公式アクティブ一覧の上位500件を初期の取得候補にする（想定バッファ300〜500件の上限から開始）。日本語向け判定後の対象だけ詳細取得し、総同接順／公開側人数順それぞれのTOP100を作る。
- UIはSteam公式のランキングを参考にする。
- 配色はVRChatのダークメニューを参考にした紺・シアン。PC版を直接開く起動リンクを一覧・詳細に配置する。
- 収集・集計はConoHa VPS、画面公開はCloudflare。まず無料枠を目標にする。
- ローカル開発後、公開GitHubリポジトリとCloudflareのworkers.devへ公開する。ユーザー指示により収集はVPSのsystemd timerで完全自動化し、ローカルの実データモードは結果の取り込みだけを行う。

## 既存環境

- Ubuntu 24.04.3 LTS。確認時の利用可能メモリ513 MiB、ディスク空き87 GB。
- `world-compass-collector.service` が専用ユーザー `worldcompass` で稼働。
- コード：`/opt/world-compass-collector/collector.py`。
- 稼働DB：`/var/lib/world-compass-collector/collector.sqlite`。
- 公開情報のスナップショット：`/var/lib/world-compass-collector/public.sqlite`。
- DBはSQLite。稼働DBは約170 MB、スナップショットは約166 MB。
- 最初の確認時、稼働DBのワールドは54,152件、スナップショットは53,117件。後の一貫した読み取りでは稼働DBは54,168件。収集中なので件数は増える。

## 保存内容

`worlds(id TEXT, record TEXT, fetched INTEGER)` にJSON形式のワールド情報がある。

名前、説明、作者名、タグ、対応端末、収容人数、サムネイル参照、VRChatリンク、取得日時を保存している。
`occupants`、`publicOccupants`、`privateOccupants`、`favorites`、`visits`、`heat`、`popularity` は調査した全レコードに存在しなかった。元APIの値が正規化処理で保存対象から外れている。

`collection_memberships` の分類は検索によって発見した経路であり、ワールドの内容を確認したジャンルラベルではない。

現在の収集は新しいワールドを見つけて保存する処理。ワールドの保存には `INSERT OR IGNORE` を使い、既存レコードを毎時更新する仕組みではない。人数履歴もない。

## 日本語候補の精度

既存の判定は、名前・説明・タグのかな／漢字、日本関連の語、作者名のかな／漢字を使う。日本語タグや関連作者の検索は優先される。日本語関連の候補を広く収集する方式で、日本語話者向けであることを保証するリストではない。

54,168件を簡易集計した結果（排他的な分類）：

| 判定の根拠 | 件数 |
|---|---:|
| 名前・説明・タグにかながある | 38,240 |
| かなはないが日本関連の明示的な印がある | 909 |
| 上記がなく作者名にかながある | 5,539 |
| その他の弱い根拠 | 9,480 |

この集計は厳密な言語判定ではない。既存DBにはThe Black CatやVRChat Homeなども含まれる。DBへの収録とランキングへの掲載を分ける必要がある。

ユーザー選択により、名前・説明・タグの根拠を中心に掲載する。上の簡易分類では38,240 + 909 = 39,149件が初期候補になるが、最終掲載数ではない。日本への言及だけの海外ワールドや、日本語説明があっても日本語話者向けではないワールドは誤判定になり得る。手動除外を自動判定より優先する。判定はランキング専用コードに実装し、既存のWorld Compass収集処理は変更していない。

## 毎時収集の現実性

既存クローラーは通常2秒以上の間隔でリクエストし、429・ネットワークエラー・サーバーエラーに待機処理がある。
同じ間隔で54,168件の詳細を個別取得すると約30.1時間かかる（待機・通信時間を除く）。全DBの詳細を毎時取得する構成は適さない。

推奨案：

1. 既存DBを読み取り、掲載候補のワールドIDと基本情報を取り込む。
2. 毎時、公式アクティブ一覧を100件ずつ最大5ページ、上位500件取得し、掲載候補と照合する。新しい掲載候補も低頻度で再読込する。DB未収録のワールドは詳細取得して掲載判定する。
3. その時点のアクティブ一覧に登場したワールドを今回の順位対象にする。前回掲載されていても一覧から外れたワールドは今回の順位から外し、履歴は残す。外れたことを0人として記録しない。手動追加は日本語向け判定を上書きするが、アクティブ一覧外のワールドを順位対象に加えるものではない。
4. 絞った対象だけ詳細を取得し、総人数・公開側・非公開側を別の履歴DBに保存する。
5. 集計済みの最小限のデータをCloudflareへ送る。

一覧候補の網羅性、取得アカウントによる差、Group系の人数集計は実測が必要。候補を限定した状態で世界全体・日本語ワールド全体の正確な順位を保証しない。「収集対象内の順位」と掲載範囲を明示する。

上位500件は日本語向け判定前の候補数であり、日本語向け500件を保証しない。掲載対象が100件未満なら取得できた件数のみ表示し、過去のデータや架空の数値で補完しない。候補の取得ページ数・掲載対象数・観測時刻を記録する。ページ取得中の順位変動による重複はワールドIDで除去する。

## 既存サービスからの分離

- 新しい収集コード・履歴DB・サービスを既存サービスと分ける。元DBと認証ファイルを読み取るため実行ユーザーは既存の専用ユーザー `worldcompass` を使用し、systemdで元ディレクトリを読み取り専用にする。
- 既存DBは読み取り専用。既存のスナップショット生成処理も変更しない。
- 既存の認証ファイルを無断でコピー・共有・更新しない。認証運用とAPI全体の取得間隔は実装前に設計する。
- DB全体、セッション、ユーザー情報をCloudflareへ送らない。
- 元データには個人用キャッシュ／再配布許諾なしという利用目的の注記がある。これは収集コードが付けた注記であり、権利元の許諾を示すものではない。公開画面での説明文・画像などの扱いは別途整理する。

## 画面・履歴

- 順位、サムネイル、ワールド名、総人数、公開側人数、1時間前からの増減を基本列にする。
- 非公開側人数と推移は詳細でも表示できるようにする。
- 総人数順／公開側人数順を切り替える。
- 時刻はJST。観測開始・終了時刻と欠測を記録する。
- 24時間ピークは「毎時観測の最大値」。時間内に発生した真のピークではない。
- 対応端末が不明なレコードを非対応と扱わない。
- 取得失敗や認証切れを0人として保存しない。
